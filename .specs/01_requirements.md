# 需求規格: 後台歷史資料匯入功能 (Historical Data Import)

## 背景 (Context)
目前的 `souvenirs` 資料主要依賴爬蟲或外部同步更新。管理者希望有一個介面 (UI)，能夠手動匯入「資前紀錄」(歷史股東會紀念品資料)，以補齊過往缺失的數據或進行大量資料修正。

## 使用者故事 (User Stories)
- **作為** 系統管理者 (Admin)
- **我想要** 在後台頁面有一個檔案上傳區塊
- **以便** 我能上傳既有的 CSV、Excel 或 JSON 檔案，批次匯入系統。

## 目標 (Goals)
- [ ] 提供一個後台介面，支援檔案拖曳上傳 (Drag & Drop)。
- [ ] 支援多種檔案格式：**CSV, Excel (.xlsx, .xls), JSON**。
- [ ] **年份指定**: 上傳時需選擇目標年份 (例如: 2024, 2025)，以解決檔案中日期未標示年份的問題。
- [ ] 系統自動解析檔案內容並轉換為統一格式。
- [ ] 解析後寫入 `public.souvenirs` 資料表。
- [ ] 處理重複資料 (Upsert) 或略過。
- [ ] **帳號管理**: 管理者可查看所有使用者列表；一般使用者僅能查看自己的資料。

## 功能需求 (Functional Requirements)
1.  **匯入介面**: 在 Admin Dashboard 增加一個「資料匯入」區塊，支援檔案選擇或拖曳。
2.  **檔案支援**:
    -   **CSV**: 需處理編碼 (UTF-8, Big5 等常見問題)。
    -   **Excel**: 支援多工作表 (預設讀取第一張 sheet)。
    -   **JSON**: 標準陣列格式。
3.  **指定年份 (Target Year)**:
    -   UI 提供年份選擇器 (例如 2024, 2025)。
    -   若檔案中的日期欄位缺少年份 (例如 "06/20")，則自動補上所選年份。
    -   若檔案中的日期已有年份 (例如 "113/06/20")，則以檔案為主，但若與所選年份不符需提示警告。
4.  **欄位對應**: 系統需能識別並對應關鍵欄位 (`code`/代號, `name`/公司名稱, `souvenir_item`/紀念品, `meeting_date`/開會日期)。若欄位名稱不符，應提供簡單的 mapping 機制或預設邏輯 (本階段先採寬鬆比對：如 "代號", "Stock Code", "code" 皆可)。
5.  **預覽與確認**: 解析後先顯示前 5 筆預覽，確認無誤後才執行寫入。
6.  **執行**: 點擊按鈕後，呼叫 Supabase Client 進行寫入。
7.  **帳號管理 (User Management)**:
    -   Admin Dashboard 增加「帳號管理」區塊。
    -   列表顯示所有註冊使用者 (`profiles`)。
    -   顯示欄位: Email, 註冊時間, 角色 (Role)。
    -   一般使用者登入後看不見此區塊。

## 限制 (Constraints)
- 必須驗證 Admin 權限 (RLS Policy & UI Guard)。
- 瀏覽器端解析 (Client-side parsing) 以減輕後端負擔，但需注意大檔案效能 (限制檔案大小 ex: < 10MB)。
